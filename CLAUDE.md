# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Platforms / OS versions:** **visionOS 27** (main app, deploy target 27.0) + **iPadOS 27** (the optional "LumaStage Control" iPad companion target). Both require **Xcode 27** (OS 27 SDK + on-device Foundation Models).

LumaStage is a **visionOS** AI stage-lighting design app. It opens an immersive 1:1 night-outdoor stage digital twin (`ImmersiveView`, RealityKit) with a floating AI conversation box: a voice/typed prompt → AI generation (**OpenAI cloud primary → on-device Apple Foundation Models fallback**, see "AI backends" below) → a cue-based lighting look applied with animated transitions. A **music-show pipeline** turns an imported/library/built-in song into an on-device analysis and a deterministic beat-locked multi-cue show — see "Music shows" below. An optional **iPad control-panel companion target** (real-time remote over Multipeer Connectivity) mirrors the conversation and edits the live look — see "iPad control panel" below; the visionOS app is the single source of truth and works standalone without it.

The immersive scene has **two modes** (`StageImmersionMode`): `.fullStage` (default — `.full` immersion, opaque night-stage venue) and `.roomSpill` (`.mixed` passthrough, where the virtual spotlights illuminate the user's real room). See "Dual immersion modes" below.

A **tabletop stage editor** (the AI composer's "Edit Stage" button) lets the user reshape the project's `StageLayout` on a small 3D diorama that ARKit rests on their **real table**. It's its own **mixed passthrough immersive space** that *replaces* the 1:1 stage space while editing — see "Tabletop stage editor" below.

> A former `LumaStage iPad` companion target (3D stage builder + per-cue micro-controls) was removed, so the cue-switching and dimmer/color controls — which lived only on iPad — are no longer surfaced in any view. `AppModel` still exposes those mutation methods (and `StageBuilderModels` still holds the builder's Foundation-only helpers), covered by the smoke tests, as reusable logic. New views use `#if os(visionOS)` / `#if canImport(...)` where platform-specific.

The product spec and MVP scope live in `docs/` (Traditional Chinese): `system-spec.md`, `demo-runbook.md`, `foundation-models-setup.md`, plus `maic-strategy.md`/`social-value.md` (competition strategy). (`docs/dynamic-rig-plan.md` and `docs/brainstorming.md` are **historical** planning/ideation docs — the dynamic-rig plan has since shipped, so its "尚未實作" status line is stale; trust this file and the specs README baseline over them.) Feature work is **spec-driven**: `docs/specs/README.md` defines the agent-executable spec format, shared conventions, and the 現況基線 (baseline of completed SPECs with their caveats) — completed specs are archived to `docs/specs/archive/`, and the README's baseline is the authoritative per-feature changelog. Code identifiers stay English, but user-facing strings are **Traditional Chinese (繁體中文)** — UI labels, status/feedback text, `aiUnderstoodCommand`/`LightingExplanation` copy, fixture-catalog names & descriptions, error messages, and the Info.plist permission strings (in `project.pbxproj`). Exceptions that stay English on purpose: the Foundation Models system prompt + `@Guide` descriptions in `FoundationModelsLightingService.swift` (the on-device model needs an English environment), the `LightCommand`/color-name parsing keywords and speech `contextualStrings` (they match English voice/text input), the cue `.name` data values `"Opening"`/`"Highlight"` (pinned by tests; mapped to 開場/重點 via `LightingCue.localizedDisplayName`), and `englishName` in the fixture catalog (shown as the English reference term beside the Chinese name). Voice input supports mixed Chinese/English. When translating, keep `localizedDisplayName` and the smoke-test–pinned English data in sync.

## Commands

### Build / run the app (requires Xcode 27)

The app uses on-device Apple Foundation Models and deploys to **visionOS 27**, so it needs **Xcode 27** (FoundationModels macro plugin + OS 27 SDK). `xcodebuild` is not available with Command Line Tools alone; point a build at an Xcode 27 install via `xcode-select` or a one-off `DEVELOPER_DIR`:

```bash
export DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer   # the Xcode 27 install (default xcode-select points at CLT)
```

Two targets/schemes (both shared): `LumaStage` (visionOS, deploy 27.0; links the local SwiftPM package `Packages/RealityKitContent`) and `LumaStageControl` (the iPadOS 27.0 companion panel — see "iPad control panel" below).

```bash
# Pick a concrete destination from: xcodebuild -showdestinations -scheme LumaStage
xcodebuild -scheme "LumaStage" -destination 'platform=visionOS Simulator,name=Apple Vision Pro,OS=27.0' build

# Build-only verification (the specs' canonical check — no device pick needed); pass = "** BUILD SUCCEEDED **"
DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer xcodebuild -scheme LumaStage \
  -destination 'generic/platform=visionOS Simulator' -derivedDataPath /tmp/lumastage-dd build
```

Pre-existing, known-non-error noise in a green build: Multipeer `Sendable` warnings, and MCSession delegate-signature lines that merely contain the word `error:` — don't chase them.

Day to day, building/running in the Xcode GUI is the normal path. The scene is a small plain window (`ContentView`) plus a full `ImmersiveSpace` (`ImmersiveView`). Generation is available when **either** backend is: an OpenAI key in the Keychain, or Apple Intelligence enabled on the device. When neither is available the AI box shows the combined reason and Send/mic are disabled.

`Tests/LumaStageCoreSmokeTests.swift` runs every check sequentially from `static func main()` using `expect` / `expectThrows` (failures call `fatalError`). **Keep FoundationModels out of the smoke-test compile set.** `canImport(FoundationModels)` is true even under Command Line Tools, so all FoundationModels references live in `FoundationModelsLightingService.swift` and `AppModel.swift` (which the harness does **not** compile). `LightingAIService.swift` stays Foundation-only; the smoke tests cover the AI→domain boundary via `LightingLookDraft`, not the model call.

### AI backends (OpenAI cloud primary → on-device FM fallback, SPEC 10)

The default generation chain (`AppModel.makeDefaultLightingClient()`) is `FallbackLightingService(primary: OpenAILightingService(), secondary: FoundationModelsLightingService())`:

- **`OpenAILightingService`** — OpenAI Responses API with strict `json_schema` structured output (model `gpt-5.5`). Deliberately **Foundation-only** (`URLSession` behind the injectable `HTTPSend` seam, key via `apiKeyProvider`), so it and `FallbackLightingService`/`OpenAIKeychain` sit in the smoke compile set. Available iff a non-empty API key exists in the Keychain (`OpenAIKeychain`; set via the gear on `ProjectSelectionView` → `OpenAISettingsView`). All its failures surface as `.generationFailed(<繁中>)` — never `.modelUnavailable`, whose message hardcodes an "Apple Intelligence 無法使用" prefix.
- **`FoundationModelsLightingService`** — on-device, no key/no network; requires Apple Intelligence (supported device, enabled in Settings, model downloaded). See `docs/foundation-models-setup.md` and "AI service shape" below.

`FallbackLightingService` (Foundation-only pure composer) is `.available` when **either** backend is; on a primary failure it falls back for any error except `.emptyPrompt`, and `result.source` reports whichever engine actually produced the look (drives `generationStatus`/the iPad panel). Both backends assemble through the same `LightingLookDraft` validators — the validator stays the single authority on counts/ranges/hex.

## Architecture

### Layering: testable core vs. thin views

The defining convention: **all pure logic — data models, validation, geometry, render order, layout math, AI parsing — lives in `Foundation`-only files**, and SwiftUI views are thin consumers. This is what lets the smoke tests run headlessly without a simulator.

- **`LightingModels.swift`** — `LightingLook` / `LightingCue` / `FixtureGroup` / `FixtureColor` / `FixtureFineControl`, the `CuePatch` enum, `StageState`, `LumaStageProject`, and `ValidationError`.
- **`LightingAIService.swift`** — Foundation-only generation contract (`LightingLookGenerating`, `LightingModelAvailability`, `LightingGenerationResult`) and the testable AI→domain assembler `LightingLookDraft.makeValidatedLook()`. No FoundationModels import.
- **`FoundationModelsLightingService.swift`** — on-device implementation: an `@Generable GeneratedLightingLook` filled by `LanguageModelSession`, mapped into `LightingLookDraft`. Guarded by `#if canImport(FoundationModels)`.
- **`StageBuilderModels.swift`** (largest file) — the shared stage geometry the visionOS renderer consumes: `StageLayout` / `StageObject` / truss geometry / presets / `ImmersiveStageGeometryPlan`. Also holds the immersion-mode policy: `StageImmersionMode` and the Foundation-only `SurroundingsLightPolicy` (pinned by `surroundingsLightPolicyGatesOpaqueVenue`). The tabletop editor's pure logic lives here too: `StageLayout.trussNodeSnap` → `TrussNodeSnap` (the connector-node snap rule, shared by the live drag and the committed `snappedObject`), `TabletopStageEditing` (preset swaps), and `TabletopSurfaceSelection` + `DetectedHorizontalSurface` (which real table to rest the diorama on). `ImmersiveSceneReopenPolicy` — the retry backoff `ContentView.reconcileImmersiveScene` sleeps on when visionOS rejects an immersive-space open mid-swap (see "Tabletop stage editor") — lives here too, as does `AIComposerPlacement`, the drag clamp for the composer's *former* in-scene attachment: unconsumed now that the composer is a real window, but still smoke-pinned — don't let its doc comment convince you the composer is an attachment. It also still holds the pure-logic layout/policy helpers from the removed iPad stage builder. Two of them are **still live** — `AppModel.selectStageObject` routes through `StageBuilderSelectionPolicy` and `addStageObject` through `StageBuilderDropPlanner`, both driven by the tabletop editor. The rest (`StageBuilderPanelLayout`, `IPadRootLayout`, `StageBuilderZoom`, `StageBuilderToolbarLayout`, `StageBuilderViewportGround`, `StageBuilderRenderOrder`, `StageBuilderInspectorPolicy`) have no consumer now, but the smoke tests still pin them, so they remain as tested, reusable logic.
- **`LightingFixtureCatalog.swift`** — fixture vocabulary metadata.
- **`StageLightAccessibility.swift`** — Foundation-only VoiceOver copy for the on-stage lights (`identityLabel`/`stateValue`, plus a hex→繁中 colour-name bucketer keyed on chroma, not HSL saturation, so `#FFE9C8` reads as 暖白 not orange). `ImmersiveView` sets these as the `AccessibilityComponent` label/value on each light's `lightpick_<n>` pick proxy (identity at build, `value` refreshed every relight in `apply`), so VoiceOver can sweep the rig and hear "第 3 盞燈，搖頭光束燈" → "藍色，亮度 60%" / "已關閉". Smoke-tested (`stageLightAccessibilityLabelsAreLocalized`).

When adding behavior to a view, **extract the decidable part into one of these model files and add a smoke test for it** rather than burying it in the view.

### State flow

`AppModel` (`@MainActor @Observable`) is the single source of truth, injected via `.environment(appModel)` from `LumaStageApp`. Views never mutate lighting state directly — they call `AppModel` methods, which delegate to `StageState`, which **re-validates on every mutation**. `SpeechTranscriber` (also `@Observable`) feeds transcripts in.

```
voice/typed prompt → AppModel.generate → aiClient (OpenAI → FM fallback) → LightingLook
  → rigConstraint.enforce → StageState.replaceLightingLook (validates) → AppModel (Observable) → views re-render
cue edit (AppModel.set…/selectCue) → StageState.patchSelectedCue (validates) → AppModel → ImmersiveView update
single-light voice command → LightCommand.parse → AppModel.applyLightCommand → lightOverrides / rotateFixture
```

### Lighting look invariants (enforced in `LightingLook.validate()`)

The `@Generable GeneratedLightingLook` schema constrains the model, and `LightingLookDraft.makeValidatedLook()` runs `validate()` on the result — keep the two in sync if you touch either:

- `schemaVersion == "1.0"`, `ambient.preset == standardNight`.
- The look is a **growable cue *stack***: `validate()` requires only that `cues` is **non-empty** and `selectedCueId` resolves to one of them. It **no longer** pins the two fixed ids `cue_opening`/`cue_highlight` — that hard-pin was removed (see the comment in `validate()`). Templates/`mvpDemo`/`showcaseDemo`/legacy still ship the two named cues `cue_opening` (**Opening**) + `cue_highlight` (**Highlight**); on-device generation emits `cue_0`/`cue_1`…, and music shows emit `cue_music_<i>`. The on-device AI schema caps the cue count at **2–6** (`GeneratedRigPlan.cues` `.count(2...6)`), not "exactly two".
- `intensity` in `0.0...1.0`; `color.mode == rgb`; color is `#RRGGBB` hex.
- Fixture roles (`wash`, `spot`, `frontLight`, `backgroundWash`) **no longer gate rendering** — the rig is dynamic and the renderer relights *every* fixture in the cue (`ImmersiveView.syncRig` builds one `SpotLight` per fixture and rebuilds when the fixture set changes; `apply` iterates them all). Role is now derived metadata for fine-control defaults and the relight debug panel (`LightingFixtureVisualModel.derivedRole`); a fixture's `renderModel` (its explicit `model`, else `.derived(role:zone:)`) picks the geometry + lumens. On-device generation is **two-phase (staged, SPEC 14)** so each model call's output stays inside the on-device ~4096-token window (shared input+output): **Pass 1** (`@Generable GeneratedRigPlan`) designs the whole rig — **4–12 fixtures** (`.count(4...12)`), each with a type + mount zone — plus the ordered **2–6 cue** labels (`.count(2...6)`), no colours/intensities; **Pass 2** runs **one fresh `LanguageModelSession` per cue** (`GeneratedCueDesign`: one `GeneratedFixtureState` per fixture, `.count(1...12)`), so each pass's output ≈ fixture count *N* and is **decoupled from the cue count *M*** (more cues = more bounded calls, not a bigger single output). Each on-device `GeneratedFixtureState` is deliberately slim — only `enabled` / `intensity` / `colorHex` (context-window budget); **gobo/beam/effect are not AI-authored on-device** (they fall back to role/zone defaults). The cloud `OpenAILightingService` DTO path additionally authors `beamAngleDegrees` + `gobo` in one shot (its window is large). The Foundation-only `LightingLookDraft.makeValidatedStagedLook(…)` joins the rig + the per-cue state rows into a validated look (rig id `fixture_<j>` stable across cues; cue ids `cue_<c>`), reconciling count drift defensively (a short row reuses its last entry / an empty row ⇒ off; extra states ignored) — smoke-tested by `stagedAssemblyReconcilesStateCounts` / `stagedAssemblyPreservesRigIdentityAcrossCues`. The Foundation-only two-fixture `LightingLookDraft.RenderableCue` path (forces a `frontLight` + `backgroundWash`, smoke-tested by `aiDraftGuaranteesRenderableFrontAndBackgroundFixtures`) still exists, but it now backs templates / mvpDemo / legacy looks, **not** generation.

### Editing model: cue patches, not look replacement

Cue edits go through `CuePatch` + `StageState.patchSelectedCue` and **only ever mutate the currently selected cue** — never the whole look, never the other cue. `StageState` keeps a `baselineLook`; `resetSelectedCue()` restores **only** the selected cue from that baseline. Full-look replacement happens solely via AI generation (`replaceLightingLook`).

### AI service shape

`AppModel` holds a `LightingLookGenerating` (default: the `FallbackLightingService` chain from "AI backends" above; injectable for tests/previews). Before generating, `AppModel.generate` refreshes `modelAvailability` from `aiClient.availability`; if the whole chain is unavailable it surfaces the reason and **does not generate**. After a successful generation, `RigConstraint.enforce` (the project's locked-rig equipment profile — see "Music shows") and `enforcingTrussMountedLasers` normalize the look before it's applied. The on-device `FoundationModelsLightingService` runs **staged (two-phase) `@Generable` generation (SPEC 14)** — a rig-plan pass then one fresh `LanguageModelSession` per cue (see "Lighting look invariants" above) — with `includeSchemaInPrompt: false`. Sampling is **randomized nucleus sampling with no fixed seed** (`GenerationOptions(samplingMode: .random(probabilityThreshold: 0.9), temperature: 0.9)`, reused across both passes) so each generation differs — an earlier `.greedy` setting made every run for a given prompt byte-identical (and silently ignored `temperature`), which surfaced as "the output is always the same"; the `@Generable` schemas still pin the structure, so randomness only varies colors/intensities/mood/wording. It joins the passes through the Foundation-only `LightingLookDraft.makeValidatedStagedLook()`, and presents user-facing errors via the OS 27 `LanguageModelError` cases. On-device generation can't run headlessly, so the smoke tests cover the `LightingLookDraft` staged-assembler/validation boundary instead of the model call.

### Live light control: three state layers + voice commands

Light state lives in **three homes**, resolved at relight time — don't invent a fourth:

1. **The recorded look** — per-cue `FixtureGroup` (color/intensity/`effect`/`aimOffset`/`manualPosition`), persisted with the project. Edited via `CuePatch` or the rig-identity fixture methods.
2. **`AppModel.lightOverrides`** (`[Int: LightOverride]`, keyed by on-stage light number) — the transient per-light manual overlay driven by voice commands and the in-headset control card.
3. **`AppModel.groupMasters`** — the transient group-fader overlay (`FixtureGroups.swift`, Foundation-only, smoke-tested): `StandardFixtureGroup` masks auto-seed from role/zone/renderModel on every look change; resolution is `LightOverride.resolved(cueColor:cueIntensity:groupMaster:)` — `final = isOff ? 0 : overrideIntensity ?? cueIntensity × master`, multiple groups take **HTP**, a per-light override beats the master, and color is never affected by a master. Ridden from the iPad panel's fader bank.

Layers 2–3 are cleared on `openProject`/`generate` (an AI regeneration replaces the rig, so overlays — like `manualPosition`/`aimOffset` — don't survive it).

**Single-light voice/typed commands** parse via the Foundation-only `LightCommand.parse` (English keywords: "turn off light 2", "set light 1 to blue", "dim light 2 to 30%", "blackout", 把 Front Light 改成紅色…) and route through `AppModel.applyLightCommand`; a numberless phrase parses to `nil` and falls through to full-look generation. `StageVoiceCommand` handles stage-level phrases; `SpeechNarrator` speaks the 繁中 feedback back. **Rotation (SPEC 13)**: "Light N turn right/left/up/down M degrees" → `.rotate` (must never eat "turn on/off" — regression-pinned). It persists as `FixtureGroup.aimOffset` (`FixtureAimOffset`, additive optional, pan clamped ±180°/tilt ±90°, old JSON decodes nil) — deliberately a **new** field, not a reuse of `fineControl.pan/tilt`, because the zone aim already tilts down and legacy `tilt=-35` data would double-apply. `AppModel.rotateFixture` edits the same fixture `id` in every cue (rig identity) and rotates the head geometry, the spotlight, and `LightEffectComponent.baseAim` together.

Tapping a light in-headset (its `lightpick_<n>` proxy) selects it, and `ImmersiveView` reacts (`.onChange(of: appModel.selectedLightNumber, initial: true)`; `selectedLightNumber` is eagerly read at body level so the change is observed) by opening `SelectedLightControlView` as a **native window**; manual override relights use a 0.12s short transition instead of the cue's cross-fade. The card **must stay a singleton `Window`** (`AppModel.lightControlWindowID`, "燈光控制" in `LumaStageApp`; `.plain` style, `.utilityPanel` placement), **not** a `WindowGroup` — `openWindow` on a `WindowGroup` spawns a NEW window per call, so selecting light after light piled up duplicate cards, while a `Window` re-presents the same one. (This replaced an earlier in-scene handle-bar attachment: a real window gets the system move bar and owns its position, so editing the light no longer re-seats the card.) The card's X button clears the selection, which flows back through the same `.onChange` to dismiss it; `ImmersiveView.onDisappear` also dismisses it so it can't outlive the stage. **Renderer footgun:** `syncRig` rebuilds the rig only when its per-fixture signature changes — `id|renderModel|zone|pan|tilt|manualPosition`, where pan/tilt are the **`aimOffset`'s**, rounded to whole degrees (`fineControl.pan/tilt` is deliberately not in the signature — see the tilt-doubling note above). Any property not in that signature won't re-aim/re-seat a live stage; rebuilds hard-cut (no smooth pan animation, a v1 tradeoff).

**Dynamic effects**: `LightEffect`/`LightEffectPlan` (Foundation-only) + `LightEffectComponent`/`LightEffectSystem` (RealityKit per-frame system). The per-cue per-fixture `FixtureGroup.effect` field (sweep/circle/strobe/chase) is wired through `LightingLookDraft.Fixture.effect`, but **no AI backend currently authors it** — only the deterministic `MusicShowBuilder` sets a non-nil effect. Neither generator fills it: on-device omits it for context budget, and the cloud path spends its extra window on `gobo` + `beamAngle` instead. So for a generated look `effect` is nil and `LightEffect.suggested(for:highEnergy:slot:)` (called through `LightEffectPlan.effects(for:)`) derives a deterministic effect from fixture model × cue energy. When a music show is playing, the system reads the beat clock instead of self-accumulated time (see below).

> The former DMX patch-sheet export (`DMXPatchPlanner`/`LightingPatchSheet`/`PatchSheetExportView` + the composer's 配接表 button) was **removed** (2026-07). The `DMXPatch` model field (`FixtureGroup.dmx` in `LightingModels.swift`) **stays**: `validate()` checks it, `showcaseDemo()` seeds it, the iPad panel's `dmxSummary` displays it, and two smoke tests pin it — but nothing auto-assigns addresses anymore, so don't treat the field as deletable dead code (and don't resurrect a planner without an ask).

### Music shows (SPEC 05/12 — song → on-device analysis → deterministic beat-locked cue show)

The flagship path: give the app a song → **on-device, offline** analysis via the WWDC26 `MusicUnderstanding` framework (`MusicUnderstandingService`, platform thin layer) → `SongAnalysis` (Foundation-only Codable mirror behind the `SongAnalyzing` seam) → `ShowPlan` (sections → `CueBrief`; energy = 0.6·pace + 0.4·loudness, short sections merged, ≥2 cues) → `MusicShowBuilder` — **deterministic and AI-free**, emitting a `validate()`-passing multi-cue look (cue ids `cue_music_<i>`, L/R-symmetric rig). Zero-fail by design: the demo never depends on a model call.

- **Playback + beat lock**: `MusicSyncEngine` plays via `AVAudioPlayer` anchored to `CACurrentMediaTime()` (`OSAllocatedUnfairLock`-protected, render-thread `snapshot()`); `MusicBeatClock`/`MusicBeatSync` (Foundation-only, smoke-tested) phase-lock strobe/chase/sweep to the beat grid, and cues auto-advance at section boundaries (30 Hz tick, edge-triggered). `AppModel`: `importSong` / `pickLibrarySong` / `useBuiltInDemoSong` / `playMusicShow` / `stopMusicShow`.
- **Song sources**: file import; the device music library via the `SongLibraryBrowsing` seam (`SongLibrary.swift`, Foundation-only with `LoopbackSongLibrary`, in the smoke set) implemented by `MusicKitSongLibrary` on **MediaPlayer** (`MPMediaItem.assetURL` is the only file-URL source; MusicKit itself only browses/metadata). DRM/streaming tracks have `assetURL == nil` → `.protected` and are unanalyzable **by platform design**, not a bug.
- **Built-in demo song**: `DemoTrackSynth` procedurally synthesizes an ORIGINAL 128 BPM backing track beat-locked to the pre-analyzed `demo-song-analysis.json` (`CachedSongAnalyzer`) — never bundle a copyrighted MP3. If audio fails to load, the show degrades to a clock-only beat lock rather than dying.
- **`RigConstraint`** — the project-level locked equipment profile (max fixture count + allowed models; `enforce(on:)` trims/rewrites and is idempotent). It constrains music-show rigs and is **re-applied at the end of AI `generate`**, so the profile also governs generated looks.

### Shared stage geometry

`ImmersiveStageGeometryPlan.make(from: StageLayout)` builds the visionOS stage geometry that `ImmersiveView` renders; a smoke test (`visionStageUsesIPadStageLayoutGeometry`) still pins it against the `StageLayout` model. The lit fixtures are **real RealityKit `SpotLight` entities** (visionOS 27), not translucent boxes: `addStageSpotLight` aims each spotlight's `-Z` at a stage target, and `apply(_:to:)` → `updateSpotLight` drives color/intensity/cone/soft-shadow/gobo per cue, keyed by the fixture's `renderModel`. The Foundation-only `SpotLightRenderMath` (pinned by `spotLightRenderMathMapsIntensityAndBeamAngle`) maps the cue's 0...1 intensity → photometric lumens, beam angle → cone degrees, and beam angle → `SpotLightComponent.Shadow.lightSize` (penumbra; quality is `.high` for front, `.medium` for wash). Soft shadows only render because structural meshes (truss, connectors, fixtures, deck, legs) opt into casting via `markShadowCaster` → `DynamicLightShadowComponent(castsShadow: true)` — a light's `Shadow` config alone is inert without casters; lit surfaces receive automatically. An optional per-fixture `GoboPattern` is projected via `SpotLightComponent.ProjectiveTexture` from a procedurally drawn, cached `TextureResource` — `LightingLookDraft` clears gobos on non-rendering roles (`FixtureRole.rendersProjectedGobo`). Every fixture in the cue's dynamic rig is rendered as a real spotlight (`syncRig` builds a `spot_<fixtureId>` per fixture, numbered Light 1…N in `fixtureGroups` order with a floating in-scene label). The fixture **body** is now type-specific geometry, not a generic stand/moving-head box: `addRigFixture` builds it via `FixtureRealityModel.makeStageFixture(for: fixture.renderModel, targetHeight: sceneLength(0.4), aim:)` (`FixtureSpatialScene.swift`, `#if os(visionOS)`) — the same cached procedural geometry as the fixture observatory, but recentered/untilted and shortest-arc–rotated so the model's +Z front aims at the stage target, named `model_<fixtureId>` and recursively shadow-marked (`markShadowCasterRecursively`); whether a fixture hangs or stands is **support-policy–decided, not type-decided (SPEC 15)**: `RigPlacement.support(forPosition:layout:)` → `FixtureSupport` (Foundation-only in `LightingModels.swift`, pinned by `fixtureSupportPolicyClassifiesTrussVsStand`) classifies the fixture's **resolved** position — zone-derived and hand-dragged alike — as `.hangFromTruss` only when it sits horizontally inside the truss footprint (±0.35 m margin) **and** ≥1 m above the deck; anything else is `.floorStand(topY:)` and grows the slim `strut` post (`model_<id>_post` / `laser_<id>_post`) from the floor, so side booms and FOH read as standing and **no fixture ever floats**. The tabletop editor mirrors the same policy with a per-proxy `fixture_stand` cylinder that follows XZ drags. The legacy `addFrontLightStand`/`addMovingHeadFixture` remain as unused fallbacks. **The `.laser` fixture type is the one exception that ALSO renders visible geometry**, not just an (invisible-in-air) cone: `addLaserProjector` builds an emitter head + a fan of *volumetric* beams (`laser_<fixtureId>` container). Each beam is two co-axial layers so it reads as light in the air, not a plastic rod: a thin white-hot `UnlitMaterial` core (`_beam_*`) and a wider low-alpha glow-sheath cylinder (`_sheath_*`). (An earlier third layer of additive `ParticleEmitterComponent` haze was **removed** — at true 1:1 scale it read as a weird off-axis speckle, and RealityKit particles aren't scene-lit; the core+sheath cylinders carry the aerial-beam look on their own. Don't re-add per-beam haze particles without an ask.) The numeric look (core white-hot lerp, sheath radius/alpha — keyed on cue hex + intensity) is the Foundation-only, smoke-tested `LaserScatterMath` + `LaserScatterConfig` (pinned by `laserBeamMathDerivesCoreAndSheathLayers`), living next to `SpotLightRenderMath`. `apply` recolors/gates both layers per cue via `updateLaserProjector`: the core/sheath `UnlitMaterial`s hard-cut (not implicitly animatable) and hide (`isEnabled=false`) when the laser is gated off (`LaserScatterMath.beamsVisible`); the `spot_<id>` cone still cross-fades and adds colour spill. This is the demo show-stopper — visible aerial beams over the stage. **Lasers are truss-only** (`RigPlacement.mountsOnTrussOnly` — currently just `.laser`): the renderer and tabletop editor always resolve a `.laser` onto the upstage truss (`resolvedPlacement` forces `.stageBack` geometry, and `clampedToTruss` snaps any dragged/manual position back into the truss footprint so `support` returns `.hangFromTruss`), every generation path normalizes laser zones through `LightingLook.enforcingTrussMountedLasers()` (applied in `LightingLookDraft.makeValidatedLook`, so on-device/cloud/fallback all comply; also re-applied after `RigConstraint.enforce`), and `AppModel.addFixtureToRig`/`moveFixture` force/clamp lasers to the truss — so a laser never floats or stands on the floor (pinned by `laserFixturesAreForcedOntoTheTruss`). The per-cue relight cross-fades over `cue.transition.duration` by mutating the light inside a SwiftUI `withAnimation` transaction (`SpotLightComponent` is an `_ImplicitlyAnimatableBuiltinComponent`; `Shadow`/`ProjectiveTexture` are plain components, so they hard-cut). **Footgun:** `apply(_:to:)` runs only inside the `RealityView` `update:` closure, which re-runs only when `ImmersiveView.body` re-evaluates — a `RealityView` update closure does **not** form its own Observation dependencies (WWDC25 "Better together: SwiftUI and RealityKit": treat the update closure as an extension of the view's body). So `body` must eagerly read `appModel.lightingLook` (a throwaway `let _ =`); without that read, AI generation mutates `stageState` but the scene never relights (the AI box text still updates, because `VisionAIComposerBox` reads `conversationState` directly during its own body eval). Any `@Observable` state the `update:` closure must react to has to be read at `body` level too — same footgun as the Scene-level `stageImmersionMode` read in `LumaStageApp`. The AI composer box is a **native `WindowGroup` window** (`aiComposerWindowID`, `.plain`, seated via `.defaultWindowPlacement` → `.utilityPanel`), **not** a RealityView attachment — a real window gets the system move bar and compositor-driven dragging; and because the system does **not** auto-hide an app's own windows in full immersion, `ImmersiveView.onAppear` opens it with the space and `onDisappear` dismisses it along with the light-control card. Projects with no saved layout fall back to `StageLayout.defaultStudentOutdoor()` (a 6m×3m deck under a 6m-wide, **5m-tall** portal truss — `StagePortalPreset.portal6x5`, matching how vendors rig the upstage truss well above the performers; the truss Z is derived from the deck's back edge, not hardcoded, and `trussPortalPreset` tiles each leg from stacked 2m + 1m segments up to the portal height, pinned by `tallTrussPortalBuildsLegsToFullHeight`).

**Scale is true 1:1** (`ImmersiveView.stageScale == 1.0`): one modelled metre renders as one real metre, per the spec's "1:1 digital twin". `scenePoint`/`sceneLength` are the **only** sanctioned way to place/size geometry — author everything in model metres and convert, never bake raw scene-metre constants (the old venue did, so a 0.46-scaled stage sat on a real-sized floor). `addVenueEnvironment` therefore **derives** the floor + backdrop drape from the actual stage footprint so they stay coherent at any `stageScale`. Because spotlight illuminance falls off with distance², lumens (`SpotLightRenderMath`, tuned at the original 0.46 scale) are multiplied by `lumenScaleCompensation` = `(stageScale / 0.46)²` in `updateSpotLight` and on the `PointLight` fill, so surface brightness is preserved when scale changes (the `DirectionalLight` key is lux-based, hence scale-independent). When changing `stageScale`, re-verify the lit look on device.

### Dual immersion modes (full stage ↔ room spill)

`AppModel.stageImmersionMode` is the source of truth; `toggleStageImmersion()` flips it (the sun icon in `VisionAIComposerBox`). The full↔mixed transition is wired across three files and is easy to break:

- **`LumaStageApp`** drives it with `.immersionStyle(selection: immersionStyleSelection, in: .full, .mixed)`. The selection is a **two-way `Binding`** (not `.constant`) so the system can write user-initiated immersion changes back into the model. The Scene body **eagerly reads `appModel.stageImmersionMode`** (a throwaway `let _ =`) so SwiftUI re-evaluates the Scene when the in-space toggle flips it — a property read only inside the lazy binding closure would not be observed.
- **`ImmersiveView`** reacts in its `update:` closure: it hides the opaque venue container (named `opaqueVenueName`, grouping floor + backdrop) per `SurroundingsLightPolicy.includesOpaqueVenue(in:)` so passthrough shows through, and applies `.preferredSurroundingsEffect(.dim(...))` in room-spill.
- Spotlights tag themselves with `SpotLightComponent.SurroundingsLight()` (visionOS 27) so they illuminate the real room in passthrough; it's inert in full immersion, so it's always set.

The opaque-venue gating decision lives in `SurroundingsLightPolicy` (Foundation-only, smoke-tested) rather than in the view — extend that enum, not the view, when adding mode-dependent geometry.

### Tabletop stage editor (real-table diorama, swapped immersive space)

The "Edit Stage" button (`VisionAIComposerBox.openStageEditor`) opens `TabletopStageEditorView` (`#if os(visionOS)`) — a small editable 3D twin of the project's `StageLayout` that **ARKit rests on the user's real table**. Editing is its **own dedicated mixed (passthrough) `ImmersiveSpace`** (`AppModel.tabletopEditorSpaceID`, declared in `LumaStageApp`): passthrough is required so the camera can see the real table and content can anchor to it. Edits persist via `AppModel.saveStageLayout`, so the 1:1 stage reflects them on return.

- **Two immersive spaces, swapped — never coexisting.** Only one immersive space can be open at a time, so entering editing *replaces* the stage space. The swap is coordinated through `AppModel.desiredImmersiveScene` (`enum ImmersiveScene { none, stage, tabletopEditor }`) reconciled by **`ContentView`** — the always-recreated main window. The hand-off is two-step and must stay this way: the leaving space's caller sets the desired scene + calls `dismissImmersiveSpace()`; that space's `onDisappear` reopens the main window; the recreated `ContentView.task(id: desiredImmersiveScene)` runs `reconcileImmersiveScene()` which opens the next space. **Footgun:** drive the open from `ContentView` (the main window), never from inside a space — a space is torn down mid-transition, so it can't reliably open its successor. The swap is hardened against **two system races** (the "stage never reopens after tabletop editing" failure): visionOS intermittently rejects an `openImmersiveSpace` issued while the previous space's dismiss transition is still winding down, so `reconcileImmersiveScene` first waits out `immersiveSpaceState == .inTransition` in 50 ms steps (a superseded reconciler task resets `.inTransition` → `.closed` as it's cancelled; it must wait, not bail, or `desiredImmersiveScene` strands with no reconciler left) and retries on `ImmersiveSceneReopenPolicy`'s backoff (Foundation-only in `StageBuilderModels.swift`: 0.3s/0.6s/1.2s, 4 attempts, pinned by `immersiveSceneReopenPolicyBacksOffThenGivesUp`) and on exhaustion gives up **visibly** — clearing `desiredImmersiveScene` so the main window falls back to the AI composer (its 開啟舞台 button re-requests the stage) instead of stranding the user on the clear placeholder with a desired scene no reconciler will honor; and because the system can also drop the `openWindow(mainWindowID)` a closing space issues from `onDisappear` (same class as the dropped `dismissWindow` covered under "Fixture observatory"), `openStageEditor`/`finishEditing` re-issue that idempotent `openWindow` right after their `dismissImmersiveSpace` as a second line of defence, covering both swap directions. Both spaces' `onAppear`/`onDisappear` dismiss/reopen the main window and set `immersiveSpaceState` exactly like `ImmersiveView`. `openProject` sets desired `.stage`; `closeProject` sets `.none`; `enterTabletopEditing`/`exitTabletopEditing` flip between `.tabletopEditor`/`.stage` (and `TabletopStageEditorView.onDisappear` re-calls `exitTabletopEditing()` if `isEditingTabletopStage` is still set, so closing the editor space via system chrome — not the 完成 button — still swaps back to the stage); `ToggleImmersiveSpaceButton` also routes through `desiredImmersiveScene` (so "關閉舞台" doesn't get instantly reopened by the reconciler). (This replaced the older `autoOpenedStageProjectId` guard + a volumetric editor window.)
- **Float-until-table, then rest.** `detectTableAndRest()` runs an `ARKitSession` + `PlaneDetectionProvider(.horizontal)` and feeds each plane (centre, footprint, table classification, and **up-facing** flag derived from the anchor's world normal) to the Foundation-only, smoke-tested `TabletopSurfaceSelection.bestSurface`, moving the diorama's `placement` container onto the winner. **Only up-facing, table-classified surfaces with a ≥0.3 m-per-side footprint qualify** (`minimumExtent`; largest → nearest) — the floor, the ceiling (large *horizontal* planes `PlaneDetectionProvider` also reports — the down-facing normal + non-table class exclude them; this was a real bug where the model stuck to the ceiling), and any other horizontal plane are rejected. Until a real table appears the model floats in front of the user (`floatingPlacement`); it stays put if the table later drops out of tracking. Degrades silently to floating when plane detection is unsupported/unauthorized (simulator, denied permission). Requires `NSWorldSensingUsageDescription` (in `project.pbxproj`). `TabletopStageScene.seatAssemblyOnSurface` seats the diorama's visual bottom on the `turntable` origin so it sits *on* the surface.
- **Entity hierarchy: `placement` → `turntable` → assembly.** `placement` is positioned by ARKit (translation only) and also carries the control-bar attachment, so the bar stays facing the user. `turntable` (a child of `placement`) spins the **whole model** about Y — the "舞台左轉/右轉" buttons (`rotateStage(by:)`, 45° steps, animated via `Entity.move(to:)`) let the user view any side, distinct from "旋轉所選" which rotates only the selected `StageObject` 90°. Keeping the spin on `turntable` (not `placement`) is what lets the model rotate without carrying the controls around or fighting ARKit's position writes. `TabletopStageScene.sync`/`seatAssemblyOnSurface`/`updateSnapIndicator` all operate on `turntable`.
- **Geometry + editing logic.** `TabletopStageScene` (in the view file, RealityKit-bound) builds one selectable container per `StageObject` (`stageobj_<id>`); the control bar is a RealityView **attachment**. Add/remove objects via `AppModel.addStageObject(assetId:)`/`removeSelectedStageObject` (truss segments, the renderable type). Dragging a truss **live-snaps to a nearby connector node** the instant it's within `connectorSnapThreshold` (a glowing marker shows the node), sharing the exact pure rule used on commit: `StageLayout.trussNodeSnap` → `TrussNodeSnap` (smoke-tested by `trussNodeSnapMarksActiveConnectorNode`), which `snappedObject` also uses. The snap marker is parented to the *assembly* (not the turntable root) so it shares the diorama's scene-unit space and stays correct under the seat offset.
- **Placing rig fixtures (lights) on the diorama.** Beyond truss/deck (which live in `StageLayout`), the editor also places the look's **rig fixtures** (which live in `cue.fixtureGroups`, NOT `StageLayout`). `TabletopStageScene.syncFixtures` builds one `tabletopfixture_<fixtureId>` proxy per fixture (parented to the same assembly as `stageobj_`), positioned by replicating `ImmersiveView.syncRig`'s per-zone slot/count counting → `RigPlacement.resolvedPlacement(fixture:slot:count:layout:)`. `selectTap`/`moveDrag` route by entity prefix (fixture ↔ stageobj selection are mutually exclusive); a fixture drag is free XZ (Y preserved, no node-snap) and commits via `AppModel.moveFixture(id:toX:y:z:)`. The control bar's "新增燈具"/"刪除所選燈具" call `addFixtureToRig(model:zone:)`/`removeSelectedFixture()`. A dragged fixture carries a `FixtureGroup.manualPosition` (additive optional, old looks decode nil) that `RigPlacement.resolvedPlacement` prefers over the zone-derived position (aim stays zone-derived) — this is the **single** placement entry point the renderer and editor share, so the light lands at the same spot on the 1:1 stage. Fixtures have **rig identity**: `AppModel`'s fixture methods edit the same `id` in *every* cue (go through `replaceLightingLook` + persist); `selectedFixtureId` is the editor's selection (cleared on `openProject`/`generate` alongside `lightOverrides`). `validate()` enforces no fixture count, so the add cap (`maxRigFixtureCount = 12`) and "don't empty a cue" remove guard live in `AppModel`. AI regeneration replaces the rig, so manual positions are lost across generation (same as `lightOverrides`).

### Fixture observatory (two windows: volumetric model + info card)

The Fixture Guide sheet (`LightingFixtureIntroView`, reachable only from `ProjectSelectionView`) is a compact grid of cards — each keeps its cheap SceneKit thumbnail (`LightingFixtureModelPreview`) so every fixture is visible at once. The catalog (`LightingFixtureCatalog.allFixtures`) is **keyed on `LightingFixtureVisualModel`, not `FixtureRole`** (so it can hold more fixtures than there are cue roles): the four abstract role-teaching fixtures (`washBar`/`spotBarrel`/`frontFresnel`/`backgroundBatten`, each mapped 1:1 to a cue `FixtureRole`) plus real-world product fixtures (`ledStrobeBar`/`movingHeadBeam`/`ledPar`/`audienceBlinder`/`ledFresnel`/`laser`). Each item's `role` is now just a teaching annotation (several products share a role); the item's `id` is its `visualModel`. Tapping a card calls `appModel.startFixtureInspection(model:)`, opens the volumetric model window (`AppModel.fixtureObservatoryWindowID`), and dismisses the sheet; the info card (`fixtureInfoCardWindowID`) is opened by `FixtureObservatoryView.onAppear`, **deliberately staged** — the card's `.defaultWindowPlacement` seats it `.trailing` the model window, and opening both windows together from the Guide raced that placement lookup and overlapped them.

The two windows are intentionally **separate, independently movable objects** (not one fused panel): a volumetric `WindowGroup` holding the 3D model (`FixtureObservatoryView`) and a plain `WindowGroup` holding the info card with paging + back controls (`FixtureInfoCardWindow`). Both are declared in `LumaStageApp` and **must inject `.environment(appModel)`** (windows opened via `openWindow` don't inherit the opener's environment). Because the Guide only opens before entering the stage `ImmersiveSpace`, these windows never coexist/conflict with the stage.

- **Project window is dismissed during inspection**: the launch/project `WindowGroup` carries an explicit id (`AppModel.mainWindowID`) and is **dismissed** while the observatory is open — `FixtureObservatoryView.onAppear` calls `dismissWindow(id: mainWindowID)`, and the three teardown sites (`close()` + both windows' `.onDisappear`, guarded by `isInspectingFixture`) call `openWindow(id: mainWindowID)`. Same dismiss/reopen happens for the immersive stage in `ImmersiveView.onAppear`/`onDisappear`. This **replaced** an older "render a 1×1 `Color.clear` view" hide trick, which left the window alive — and visionOS keeps drawing a live window's empty, draggable move/grabber bar, so the user saw a stray bar with nothing in it. A live window's bar can't be hidden via API; the window must actually be dismissed. `ContentView` still renders `Color.clear` for the `.open`/`isInspectingFixture` states as a one-frame fallback (so it never flashes a duplicate composer box if the dismiss lags). **Footgun:** dismissing/reopening the main window recreates `ContentView`, so open/close guard state must live in `AppModel`, never in `ContentView` `@State` — otherwise the recreated `ContentView.task` reopens the stage the user just closed. (Today that guard *is* the `desiredImmersiveScene` reconciler; the interim `AppModel.autoOpenedStageProjectId` field is gone.) **Footgun 2:** because closing the stage reopens the main window, "Back to Projects" (`VisionAIComposerBox.returnToProjects`) must call `closeProject()` **before** `dismissImmersiveSpace()` — if a project is still selected when `onDisappear` reopens the main window, that fresh window comes up on the AI composer (ContentView's project-open branch) and can stick there instead of the project list. Clear the project first; then the reopened window shows `ProjectSelectionView` with no race. As a second line of defence (a `dismissWindow` issued during the immersive-space close transition is *intermittently dropped* by the system, stranding the AI composer's own window), `ContentView`'s `ProjectSelectionView` branch re-dismisses `aiComposerWindowID` in `.onAppear` — the project list must never coexist with that window, so re-dismissing whenever the list appears is a safe, idempotent invariant.
- **Shared paging state lives in `AppModel`, not the view**: both windows read/write `appModel.fixtureCarousel` (a Foundation-only `FixtureCarousel` in `LightingFixtureCatalog.swift`, pinned by `fixtureCarouselPagesAndWraps`; keyed on `[LightingFixtureVisualModel]` with wrap-around `advance(by:)`/`select(model:)`). Paging on the card drives the model window and vice versa — that's why the carousel can't be view `@State`.
- **Lifecycle**: the info card's back button (`onBack`) calls `endFixtureInspection()` + dismisses both windows. Each window's `.onDisappear` also tears down the sibling **guarded by `isInspectingFixture`** so closing either via system chrome cleans up without an infinite dismiss loop.
- **3D models are RealityKit**: `FixtureRealityModel.makeEntity(for:)` (`FixtureSpatialScene.swift`, `#if os(visionOS)`) rebuilds the SceneKit `LightingFixtureSceneFactory` geometry as `ModelEntity`s (RealityKit has no `generateTorus`, so rings use a small `MeshDescriptor` torus whose ring lies in X-Z to match `SCNTorus`). Each model is built once, cached, and handed out via `clone(recursive:)`; `makeEntity` recenters on visual bounds and uniformly scales to fit the volume.
- **Manipulation uses RealityKit's system gesture, not hand-rolled SwiftUI gestures**: the model is manipulable with two-hand scale + rotate; **translation is locked** (`dynamics.translationBehavior = .none`) so it spins/resizes in place like a turntable and can't be dragged off-centre or out of reach. Wired via `ManipulationComponent.configureEntity(stage, collisionShapes:)` on a stable container entity (`fixture_stage`), with `releaseBehavior = .stay` so the fixture stays where the user leaves it; `FixtureRealityModel`'s `fitTarget` (0.40m of the 0.7m volume) opens it compact, and the user pinches to enlarge. This **replaced** three stacked `.targetedToAnyEntity()` SwiftUI gestures (`DragGesture`/`MagnifyGesture`/`RotateGesture3D`) — because `MagnifyGesture` and `RotateGesture3D` are both pinch-based, stacking them as separate `.gesture()` modifiers made them fight so only one (rotate) ever took effect and scaling silently did nothing. `configureEntity` adds the input target, hover highlight, `ManipulationComponent`, and collision for you, so no manual `InputTargetComponent`/`CollisionComponent` is set. The info card window handles paging only (swipe or ‹ › buttons), so manipulation never competes with paging. `FixtureObservatoryView.sync(_:)` only swaps the model when the visual model changes (entity named `fixture_model_<visualModel>`) and re-runs `configureEntity` to refit the collision box (and re-assert `.stay`, the translation lock, and `dynamics.scalingBehavior = .unconstrained` — required explicitly: at the component default, pinch-to-scale silently did nothing on device while rotation worked) to the new model; the container transform resets to default on page change via `onChange` so each fixture is re-presented centered. (Known OS bug FB19610114: indirect-input translation can break on a physical Vision Pro when certain spatial widgets — Photos/Calendar — are placed in the room; environmental, simulator-unaffected.)

### iPad control panel (real-time companion)

An optional **iPad app target** ("LumaStage Control") is a thin real-time remote for the visionOS host over **Multipeer Connectivity** (local P2P, no server/account — chosen over iCloud, which is seconds-laggy). The visionOS app stays the single source of truth and runs standalone; the iPad mirrors its state and sends edits. The target is in the `.xcodeproj` (`LumaStageControl`, shared scheme, iOS 27.0, own `LumaStageControl/` folder for Assets/Info.plist): it compiles an **opt-in subset** of the `LumaStage/` folder via a synchronized-folder membership-exception list — the six `iPadPanel/` files plus the shared core (`LightingModels`, `LightingAIService`, `StageBuilderModels`, `LightingFixtureCatalog`, `FixtureGroups`, `LightEffect`, `RigConstraint`, `LumaStageDesign`, `LumaSyncProtocol`, `LumaSyncTransport`, `MultipeerSyncTransport`). **A new shared file the panel needs must be added to that per-file membership list** (Xcode file inspector → Target Membership), or the panel build breaks. `docs/ipad-control-panel-setup.md` documents the original setup. The link is layered:

- **Schema (`LumaSyncProtocol.swift`, Foundation-only, smoke-tested by `lumaSyncProtocolRoundTrips`)** — the transport-agnostic wire types: `LumaSyncMessage` envelope, `LumaHostState`, `LumaConversationState` + `LumaChatMessage` (Chat tab), `LumaControlCommand` (panel → host, 1:1 with `AppModel` methods), `LumaPeerRole`. Lighting payloads **reuse** the already-`Codable` `LightingLook`/`FixtureFineControl` rather than re-describing them.
- **Transport (`LumaSyncTransport.swift`, Foundation-only, smoke-tested by `loopbackTransportDeliversMessages`)** — the `LumaSyncTransport` protocol + JSON `LumaSyncCodec` + an in-process `LoopbackSyncTransport` for tests/previews. Host/panel depend on this protocol, not on Multipeer (same injectable-boundary pattern as `LightingLookGenerating`).
- **`MultipeerSyncTransport.swift`** — the real impl (host advertises, panel browses, reliable `MCSession`). **Not** in the smoke set (imports MultipeerConnectivity). The project builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, so this `@MainActor` type marks its MC delegate methods (invoked off-main) `nonisolated` and hops to main via `onMain`; the `MCSession` is `nonisolated(unsafe)` because it's thread-safe and the delegates need it off-main. Its `serviceType` (`"lumastage-sync"`) must stay in sync with the `NSBonjourServices` entries (`_lumastage-sync._tcp`/`_udp`) declared in **both** targets' `Info.plist` files — rename one without the other and local-network discovery silently fails on device.
- **Host (`LumaSyncCoordinator.swift`, visionOS only)** — owns the transport, observes `AppModel` via `withObservationTracking` (no edits to the mutation methods — it re-arms and republishes the full `LumaHostState` on any change), and applies inbound `LumaControlCommand`s by calling `AppModel`. Chat history is derived from the same observable state the composer drives (`conversationState`/`transcript`/`aiUnderstoodCommand`/`lastExplanation`); a `lastPromptEmitted` guard stops manual cue edits (which change `aiUnderstoodCommand` but not `transcript`) from replaying a stale user bubble. Started by `AppModel.startIPadSync()` from `LumaStageApp`'s main-window `.task` (idempotent).
- **Panel (`iPadPanel/`, all `#if os(iOS)`)** — `LumaPanelApp` (`@main`), `LumaPanelModel` (`@Observable`; holds the last `LumaHostState`, sends commands), `PanelRootView` (TabView: Chat + Lighting), `PanelChatView`, `PanelLightingView` topped by `PanelFaderBankView` (five vertical group-master faders with multi-touch ride, bump, latching solo, and a GO footer — driving `setGroupMaster`/`bumpGroup`; faders rest at full = 1.0, the multiplicative-master neutral). These stay in the visionOS target harmlessly (the `#if os(iOS)` makes them empty there). The host publishes full snapshots (the `.conversation`/`.lighting` delta cases exist for a future optimization); the panel's Lighting tab drives the cue API and group masters — the per-light overrides (`AppModel.lightOverrides`) aren't surfaced yet.

## Conventions

- Design tokens (colors, radii, glass panel modifiers) live in `LumaStageDesign.swift` / `LumaPanel`; the UI targets native "liquid glass" styling. Reuse these rather than hardcoding colors.
- visionOS/RealityKit views use `#if os(visionOS)`; `SpeechTranscriber` is guarded by `canImport(Speech)/canImport(AVFoundation)`, and `LightingFixtureIntroView` (SceneKit fixture previews) by `canImport(SceneKit) && canImport(UIKit)`.
- New projects start from `ProjectCreationTemplate`. `LumaStageProject.defaultProjects()` seeds **one** starter project (`project_dance_showcase`, built from `showcaseDemo()` — a 9-fixture L/R-symmetric rig with `selectedCueId` forced to `cue_opening`); it does **not** return `[]`.
