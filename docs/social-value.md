## 1. 問題:燈光設計被硬體鎖在門外

舞台燈光是一門「要先有,才能學」的手藝。今天想入門或練習一場演出的燈,你得同時擁有三樣東西:

- **一台燈控台**(grandMA2 一類)——數十萬起跳,且學習曲線陡到要數週訓練。
- **一整套實體燈具與 truss 吊掛系統**——成本、重量、用電、吊掛安全,缺一不可。
- **一個真實場館**——有黑空間、有掛點、能調暗、能架燈讓你試。

這構成一個死循環:**學燈控台,要先有一台燈控台。** 沒有器材與場地的人,連「試錯」的入場券都拿不到。學生劇團排一場成發,常常到進場當天才第一次看到自己的燈打在人身上——錯了也來不及改。

而比成本更深一層、也更少被討論的,是**這門手藝對身體的預設**。傳統燈控台是一個高度視覺、高度手動的介面:密密麻麻的推桿與編碼輪、必須盯著看的螢幕、要靠精細手部操作即時抓燈走場。這對**視障創作者**幾乎是一道無法跨越的牆——介面本身假設你看得見;對**行動或精細動作受限的創作者**同樣不友善——它假設你能穩定地操作數十個實體控制元件。於是舞台燈光成了一門被硬體與「健全者介面」雙重把關(gatekept)的創作,把一群本可以是優秀燈光敘事者的人,擋在了門外。

**這不是「沒有好工具」的問題,是「一整群人被結構性排除」的問題。**

## 2. 對象:被成本與介面擋在門外的創作者

| 對象 | 真正的障礙(具體) |
|---|---|
| **學生劇團 / 社團** | 排一場成發要燈,但社團沒預算買控台,學校的燈也得排隊借;沒有自己的空間反覆試光。 |
| **偏鄉 / 資源有限的學校** | 戲劇、展演課想教燈光設計,卻連一套示範器材都湊不齊;教學只能停在投影片與口述,學生摸不到真實的「打光是什麼感覺」。 |
| **獨立創作者 / 小型製作** | 在宿舍、在家構思一場演出的視覺,卻無從預覽;只能憑想像把設計交出去,進場才知道對不對。 |
| **視障創作者** | 傳統控台與其軟體是 sighted-only 的視覺介面;即使有滿腦子的燈光敘事,也卡在「看不見介面」這一步,無從操作、無從學起。 |
| **行動 / 精細動作受限的創作者** | 走台需要即時、連續地操作大量實體推桿與編碼輪;這對手部控制受限的人是高門檻,讓他們難以獨力跑完一場秀。 |

這五群人的共同點不是「能力不足」,而是**被一套以「有錢、有場地、看得見、手很穩」為預設的工具鏈擋在外面**。

## 3. 我們怎麼解:把每一道障礙對應到一個真實做出來的能力

LumaStage 的設計哲學,是把「擁有什麼」的門檻,換成「**能不能說出你要的畫面**」。以下每一項都是已實作、可演示的能力,不是願景。

### 3.1 一句話生成專業 cue → 降低專業門檻

使用者用自然語言描述要的氛圍(中英混講皆可),**OpenAI 雲端模型**就生成一整套 **4–12 盞燈、2–6 個有序場景(cue)** 的燈光腳本,每盞燈帶顏色、亮度、光束角與過場。

- **對障礙的回應**:把「要先學會操作一台控台」的數週門檻,壓縮成「**說一句話**」。不必先懂推桿與編碼輪,也能產出結構正確的專業 cue。
- **裝置端音樂理解仍保有隱私**:燈光腳本生成走雲端 OpenAI(需金鑰與網路),但**音樂分析**這一條旗艦流程仍**完全在裝置端離線**完成(`MusicUnderstanding`)——匯入的歌曲不上傳,分析結果留在裝置上。

### 3.2 全語音閉環:不靠視覺、不靠精細手部,也能設計並跑完一場秀

這是社會價值支柱裡最關鍵、也最具體的一塊。我們把**整個設計與操作迴圈都做成可以零觸控完成**:

- **語音生成**:用講的描述需求(`SpeechTranscriber`,支援中英混講),AI 直接生成整套燈光。
- **語音走場(GO)**:用講的跑一整場秀——「**下一個場景** / **go**」往前、「**上一個** / **go back**」往回、「**新增場景**」加一段(`StageVoiceCommand` 解析中英關鍵詞 → `AppModel.goToNextCue / goToPreviousCue / appendCue`)。這正是專業控台的 GO 鍵心智模型,只是改用一句話觸發。
- **語音改單燈**:「把 Light 5 關掉」「第 3 盞變綠」疊在 AI 結果上做精準覆寫(`LightCommand`)。
- **語音朗讀回饋〔已下架〕**:此 TTS 回饋路徑已於 2026-07-08 移除;現況只保留語音輸入與畫面文字回饋。

把這四步串起來,結論是一句話:**一個看不見螢幕、或無法做精細手部操作的人,可以從頭到尾——生成、走場、微調、聽結果——獨力完成一場演出的燈光設計。** 這不是把無障礙當外掛,而是讓整個產品迴圈本身就可以用聲音閉環。

### 3.4 1:1 空間數位孿生 + 房間溢光:把整套 rig 壓縮成一台 Vision Pro

LumaStage 開出一個**真實尺寸(1:1)的夜間室外舞台數位孿生**,燈是真的 RealityKit 聚光燈(軟陰影、gobo 投影、可見雷射光束),不是貼圖。使用者站在舞台中央,所見即所得——**不需要任何實體器材與場地**,就能判斷光有沒有打到臉、背光有沒有把人從背景分離。

更進一步,切換到 **mixed passthrough** 模式,使用者回到自己的真實房間,AI 設計的 1:1 舞台與光束就**疊在眼前的真實空間裡**。對一個沒有黑空間、沒有掛點的學生來說,這是他第一次能「身體感受到」自己設計的光在自己空間中的樣子——零器材的所見即所得。

> **誠實 caveat(visionOS 26)**:此模式切換為 passthrough(可見真實房間)+ 環境調暗,虛擬舞台與光束和真實空間**疊加共存**;讓虛擬聚光燈**實際照亮真實牆面**(`SpotLightComponent.SurroundingsLight`)需 visionOS 27+,本版尚不具備,因此我們不宣稱「光打在你的牆上」。

## 4. 一個真實場景:阿瑋的開場

> 阿瑋是大二視障學生,熱愛劇場,負責校內音樂會的燈光,但他從沒摸過燈控台——那台機器對他來說只是一面看不見的牆。

他戴上 Vision Pro,對著空舞台說:**「幫我做一場音樂會的開場,溫暖一點,收尾要明亮有能量。」**

這段故事中的語音朗讀與 VoiceOver 橋段已下架;現況只能示範語音輸入、畫面文字回饋與舞台即時變化。

滿意之後,他說「**go**」,把整場秀從開場一路走到收尾。

**他從頭到尾沒看任何一個按鈕,也沒碰任何一根推桿。**

## 5. 誠實邊界:我們明確「不宣稱」什麼

這一節是寫給最懂行的評委看的。把界線講清楚,是工程誠信,也是我們論述站得住腳的原因:

1. **不取代 grandMA2 等專業控台。** LumaStage 的定位是燈控台**之前**的設計層與 previz;最終演出仍交專業控台執行,我們未來透過 Art-Net/sACN 當它的**上游**——餵它,不取代它。
2. **不宣稱瓦特級光度學精度。** 我們的打光是真實的 RealityKit 聚光燈(0–1 亮度映射成流明、光束角映射成 cone 與陰影半影),但這是**觀感層級**的擬真,不是流明計可量測的物理精度。設計階段要的是「這感覺對不對」,絕對校正仍在真實場地——這正是我們定位在設計層而非執行層的原因。
3. **無障礙仍在持續完善,且需實機驗證。** 逐燈 VoiceOver、全語音閉環、Reduce Motion 已實作;但完整的無障礙合規與真實可用性,**必須在實體 Vision Pro + VoiceOver 上走查**才算數,我們不會在尚未實測前宣稱「完全無障礙」。
4. **燈光生成需要 OpenAI 金鑰與網路。** 燈光腳本由 OpenAI 雲端模型生成,因此需要使用者自備 API 金鑰並連上網路;金鑰未設定或無網路時,app 會誠實顯示無法使用狀態並停止生成(我們的 availability gate 是真的),不會假裝能離線生成。**但音樂分析仍是裝置端離線的**(`MusicUnderstanding`)——那條流程不上傳、不需金鑰,隱私敘事在音樂理解上仍然成立。

**這些界線不是我們的破綻,是我們的座標。** 一個說得清楚自己邊界的團隊,比一個什麼都敢宣稱的團隊更值得信任。

## 6. 可量測的社會價值(規劃中)

> 以下為**驗證計畫**,清楚標示為尚未執行,供決賽說明「我們打算如何證明影響力」:

- **與特教資源班 / 學校戲劇社試用**:邀請視障與一般學生各一組,記錄「從零到完成一個雙場景設計」的上手時間與完成率。
- **無障礙走查通過率**:依 VoiceOver / Reduce Motion / Dynamic Type 列查核表,在實體 Vision Pro 上逐項走查並記錄通過比例。
- **零器材完成度**:統計使用者在「完全不接觸實體燈具」前提下,能獨力完成一場多 cue 燈光設計、並以 GO 走完全場的比例。

這些都是**規劃**,不是已有的數據——我們只承諾說得出口的事。
